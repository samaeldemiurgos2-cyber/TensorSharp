The chat template is copied without modification from llama.cpp
`models/templates/muse-spark.jinja` at revision
`797de63b2fa7396dcc8caca76834c699ac84e1c3`.

It is a required deterministic protocol fixture; tests do not need a model or
network access. The tests verify TensorSharp rendering and streaming behavior,
not the quality or throughput of the 816B model.

`unsloth_chat_template.jinja` contains the `tokenizer.chat_template` extracted from
the first Q4_K_M GGUF shard in `unsloth/Muse-Spark-Open-816B-A42B-GGUF`, repository
revision `c00670568b6ce5e56a247f67091247984df2a01e`. It uses low=8, medium=32,
high=256, and xhigh=512 (default), unlike the local llama.cpp template. The embedded
UTF-8 string and the fixture normalized to LF have SHA-256
`2341a2d3b1f1b0ac92b6237d46e2fff495109bd3305cacdea54726f5e98411db`.
The Windows checkout's CRLF file has SHA-256
`ec021c6ce4dee90a7d779ad381beb7efb6ca08197724ccefb1fe8d314298fc9d`;
that file hash is not the embedded template hash. The downloaded UD-Q3_K_XL and
UD-Q4_K_XL templates contain the same LF string. The reference adapter generator
normalizes file newlines before rendering and records the normalized source hash.

`jinja_reference.json` contains independent Python Jinja2 3.1.6 prompt renders.
Regenerate it with `python eng/validation/generate_muse_spark_protocol_fixtures.py`.
The generator retains JSON schema property order to match llama.cpp/minja. HF
generation tags are removed because they annotate spans without changing text.

`llama_jinja_matched_reference.json` contains six renders verified with the
unchanged llama.cpp Jinja engine at the revision above. They cover control-token
escaping, typed images, tool schemas, and thinking on/off. TensorSharp's production
renderer must match them. The comparison template is generated by
`eng/validation/prepare_muse_spark_llama_reference.py`: it surrounds the complete
released source with an empty current-date setting and the no-tools direct-answer
suffix. An empty string is intentional; llama's `default` filter replaces null
with the current date. The generated template is validation configuration.

For example, after building `eng/validation/render-llama-jinja.cpp` against the
checkout's unchanged Jinja sources, regenerate the fixture with:

```text
python eng/validation/prepare_muse_spark_llama_reference.py --out docs/validation/muse-spark/prompt-parity --renderer PATH_TO_RENDERER --llama-checkout PATH_TO_LLAMA --fixture InferenceWeb.Tests/Fixtures/MuseSpark/llama_jinja_matched_reference.json
```

The Muse Spark HTTP harness sends `reasoning_format: "none"` only for reference
requests with thinking disabled and no tools, because llama's specialized Spark
parser assumes the recipient header is generated. Tool-bearing requests retain
the default routed parser. This verifies rendered input equivalence; it does not
establish inference quality, timing parity, or full tokenizer equivalence.

`vision-left-red.png` and `vision-left-blue.png` are deterministic 256×128 RGB
fixtures generated by `image_png()` in `eng/muse-spark-validate.py`. They show two
solid colored halves in opposite orders. The HTTP harness requires correct
left/right color answers for both images, so a fixed answer cannot pass. These
fixtures screen basic image integration and spatial/color understanding; they
do not establish general visual reasoning quality.

`vision-chart-a.png` and `vision-chart-b.png` are deterministic 320×256 bar charts
generated by `chart_png()` in the same harness. Explicit 5×7 bitmap glyphs avoid
platform font dependencies. The optional `image_chart` scenario requires correct
bar count, tallest/shortest labels, and the four-digit code visible only in each
image. Both the ordering and code change between fixtures. This adds basic chart
interpretation and OCR coverage without changing the default color-image test.
